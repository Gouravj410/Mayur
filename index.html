Relational Database Design

8-Table Relational Schema Architecture

Engineered for 3rd Normal Form (3NF) with strict referential integrity, ON DELETE CASCADE foreign keys, and synchronized financial calculations.

users

Customers & Admin staff authentication records.

• id (PK)
• full_name, email (UQ)
• phone, address
• password_hash
• role ('admin'/'customer')
vehicles

Automobile registrations mapped to customers.

• id (PK)
• customer_id (FK → users)
• registration_number (UQ)
• brand, model, year
• fuel_type, vehicle_color
services

Standardized workshop maintenance packages.

• id (PK)
• service_name
• description
• base_charge
• estimated_duration
bookings

Customer appointment slots & tracking status.

• id (PK)
• customer_id, vehicle_id
• service_id
• booking_date, time_slot
• status ('pending', 'approved', etc.)
repairs

Technician diagnostic job cards.

• id (PK)
• booking_id (FK → bookings)
• technician_notes
• diagnostic_details
• labor_charge, repair_status
spare_parts

Workshop parts inventory with stock counters.

• id (PK)
• part_name, part_number (UQ)
• unit_price
• stock_quantity
• minimum_threshold
repair_parts

Junction table deducting inventory stock.

• id (PK)
• repair_id (FK → repairs)
• part_id (FK → spare_parts)
• quantity_used
• unit_price_at_repair
bills

Itemized synchronized tax invoices.

• id (PK), invoice_number
• booking_id, customer_id
• total_service_charge
• total_parts_charge, grand_total
• payment_status, payment_method

Platform Capabilities & Engineering FAQs

An architectural deep-dive into transaction atomicity, multi-tier database failover, OWASP security controls, and high-concurrency workshop throughput.

Answer: Flask provides a lightweight, high-performance WSGI foundation with sub-15ms baseline request latencies and low memory overhead. By structuring the codebase into modular Flask Blueprints (Customer, Garage, Booking, Bay Diagnostics, Inventory, and Tax Billing), the platform maintains clean domain boundaries and high maintainability, making it seamless to scale or extract services independently into microservices.

Answer: The data layer (database/db.py) utilizes an intelligent connection abstraction. In standard cloud/production deployments, it maintains active connections to MySQL with transactional safety. During on-premise local workshop operations or intermittent network drops, the engine automatically catches connection exceptions and fails over to an embedded, high-performance SQLite engine (car_service.db). This guarantees zero workshop downtime.

Answer: When technicians issue spare parts to a repair job card, the operation executes within an atomic database transaction. The system locks and evaluates stock_quantity >= quantity_requested. Upon validation, it simultaneously writes an audit line to repair_parts and decrements inventory: UPDATE spare_parts SET stock_quantity = stock_quantity - ? WHERE id = ?. Any anomaly triggers an immediate rollback, preventing negative stock or phantom inventory.

Answer: 1) SQL Injection Defense: 100% of queries use parameterized prepared statements (? / %s), neutralizing injection vectors. 2) Credential Protection: Passwords undergo salted PBKDF2-SHA256 cryptographic hashing with Werkzeug before persistence. 3) IDOR & Broken Access Control: Strict session boundary verification (customer_id == session['user_id']) guarantees tenant isolation, preventing unauthorized cross-account inspection of vehicles or invoices.

Answer: Invoice calculations use a deterministic formula: Total = Service Base Labor + Σ(Part Qty × Historical Unit Price) + Statutory 18% GST. Replaced parts capture unit_price_at_repair at issuance time. As a result, closed historical invoices remain immutable and audit-compliant even if catalog wholesale part prices change in the future.
